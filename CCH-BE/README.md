# CCH Backend

Go API foundation built with Fiber v3. The backend is the planned owner of CCH business rules, authorization, and MySQL persistence. Business routes are opt-in and disabled by default. Guest ticket creation is delegated to the legacy CCH API; the narrow Call Center status transition writer uses an explicit Go-owned MySQL transaction only after the legacy status Add path is fenced. Fiber v3 requires Go 1.25 or newer.

## Run

```powershell
go run ./cmd/api
```

The service listens on `:8080` by default. Set `CCH_BE_ADDR` to override the address. `GET /healthz` is a liveness check; it does not claim that MySQL or downstream services are ready.

`GET /readyz` checks whether the configured MySQL connection can be pinged. It returns `503` when MySQL is not configured or unavailable and does not expose connection errors.

### MySQL Configuration

Set these environment variables before starting the service:

- `CCH_DB_HOST`
- `CCH_DB_PORT` (defaults to `3306`)
- `CCH_DB_USER`
- `CCH_DB_PASSWORD`
- `CCH_DB_NAME` (for the current local schema, `cch`)

The backend opens a MySQL-compatible connection only when all required values are present. Use a dedicated application account with least privilege; do not use the database administrator account. Store the password outside source control. Legacy tables are accessed only by enabled domain routes. Guest submission reads ACL/master/customer data and persists the consented intake draft; ticket creation itself goes through the legacy CCH API.

## Authentication Foundation

The legacy CCH JWT verifier reads `CCH_JWT_SECRET` and `CCH_JWT_ISSUER` from the process environment. It accepts HS512 only, requires issuer/issued-at/expiry claims, and reads bearer tokens from `X-Authorization` (raw token or `Bearer <token>`). It does not read tokens from cookies or query parameters.

The key must be rotated in the legacy issuer and provisioned through an approved secret source before interoperability is enabled. Never copy the statically configured legacy key into this repository. Do not enable the complaint read routes until rotation is confirmed. Do not protect ticket operations with signed office/role claims alone: load current account activation/lock state, office scope, and the required table/action permission from trusted CCH data first.

`internal/modules/authorization.AccessService` checks the requested table action through the `AccountAccessLoader` interface. `internal/modules/authorization/repository.MySQLAccessRepository` implements that interface with read-only account and table-permission queries. It selects no password field, revalidates current activation/lock, office, report-to, and role claims, reads permissions by the legacy project-prefixed table key, ORs current role masks, and applies a positive token mask. System Administrator level `-1` is denied until an approved identity mapping exists. `internal/platform/httpapi.RequireTableAction` consumes the verified identity, runs this action check, and exposes trusted account access to the handler. The composition root wires the Call Center read module only when explicitly enabled; its routes remain disabled by default. The returned office is trusted identity context, not a generic complaint-row filter.

### Complaint Read API Opt-In

`CCH_ENABLE_HELP_CATEGORY_MASTER_API` is an independent master-data gate and defaults to `false`; enabling it does not enable other master or help-article routes.

`CCH_ENABLE_HELP_ARTICLE_API` independently gates staff Help Article CRUD and defaults to `false`.

The default-off flag inventory below also includes the independently gated `CCH_ENABLE_DOCUMENT_TYPE_MASTER_API`, `CCH_ENABLE_HANDLING_STATUS_MASTER_API`, `CCH_ENABLE_OFFICE_MASTER_API`, `CCH_ENABLE_FOLLOWUP_STATUS_MASTER_API`, `CCH_ENABLE_HOLIDAY_CALENDAR_MASTER_API`, `CCH_ENABLE_LANGUAGES_MASTER_API`, `CCH_ENABLE_APP_SETTINGS_API`, `CCH_ENABLE_REGIONAL_ADMIN_API`, `CCH_ENABLE_CS_OFFICER_STATUS_API`, `CCH_ENABLE_USER_LEVEL_CATALOG_API`, `CCH_ENABLE_BREADCRUMB_LINKS_API`, and `CCH_ENABLE_CUSTOMER_PROFILE_API`.

`CCH_ENABLE_CALL_CENTER_COMPLAINT_READ_API`, `CCH_ENABLE_CALL_CENTER_STATUS_WRITE_API`, `CCH_ENABLE_CALL_CENTER_FOLLOWUP_PLAN_API`, `CCH_ENABLE_CALL_CENTER_FOLLOWUP_REALIZE_API`, `CCH_ENABLE_CALL_CENTER_DOCUMENT_METADATA_API`, `CCH_ENABLE_CALL_CENTER_DOCUMENT_UPLOAD_API`, `CCH_ENABLE_CALL_CENTER_DOCUMENT_DOWNLOAD_API`, `CCH_ENABLE_CALL_CENTER_DOCUMENT_PREVIEW_API`, `CCH_ENABLE_CALL_CENTER_DOCUMENT_DELETE_API`, `CCH_ENABLE_CALL_CENTER_CUSTOMER_SEARCH_API`, `CCH_ENABLE_COMPLAINT_TYPE_MASTER_API`, `CCH_ENABLE_COMPLAINT_SOURCE_MASTER_API`, `CCH_ENABLE_SHIPPING_SERVICE_MASTER_API`, `CCH_ENABLE_GUEST_INTAKE_SESSION_API`, `CCH_ENABLE_GUEST_INTAKE_SUBMISSION_API`, and `CCH_ENABLE_GUEST_INTAKE_REVIEW_API` all default to `false`. Complaint routes require MySQL and valid staff JWT configuration. Status mutation additionally requires `CCH_LEGACY_STATUS_WRITES_FENCED=true` and the additive idempotency migration described below. Follow-up plan creation and realization have independent flags. Document metadata listing is independently gated and does not enable file upload/download. Upload, binary download, inline preview, and deletion also have independent gates: upload requires private storage plus ClamAV; download/preview require private storage and metadata schema but not the scanner; delete requires private storage plus metadata schema and removes only office-owned metadata rows transactionally (the stored object is then removed best-effort). Customer search is independently gated because it returns PII. Master CRUD uses per-action CCH table ACL and defaults off. Guest session issuance requires MySQL, a separate intake signing key, explicit issuer/TTL, and an exact Origin allowlist. Guest submission and CS review additionally require the staff JWT verifier, a dedicated CCH intake account, an HTTPS CCH API base URL, and a trusted intake office code. None of these flags proves the legacy signing key was rotated or that the legacy status route was actually fenced; verify both operationally before enabling routes. Review DB permissions and use least-privilege accounts. Customer matching is not identity verification; unmatched or ambiguous profiles are held for CS review.

`internal/modules/complaints/gateway/legacycch` contains the HTTPS-only transport adapter for the legacy complaint Add API. The `intake/submission` service uses it with the configured technical account, verifies the resulting CCH JWT, and requires current `Add` permission on `cchentri`, a single Call Center role, and the configured origin office before submitting. The client does not follow redirects, bounds response size, and returns generic upstream errors. It is composed only when its feature flag is enabled.

The `internal/modules/intake/session` package provides an isolated guest conversation-token primitive with its own signing secret, issuer, audience, purpose, random conversation ID, and bounded expiry. Its default-off `POST /api/v1/intake/sessions` endpoint issues a token after exact Origin allowlisting and an in-process per-IP limit. It supports CORS preflight for configured origins. Never reuse the staff `CCH_JWT_SECRET`; production deployments also need edge-level rate limiting and a configured trusted origin list.

### Guest Intake Ticket Submission

`POST /api/v1/intake/submissions` is owned by `internal/modules/intake/submission/controller` and is registered only when `CCH_ENABLE_GUEST_INTAKE_SUBMISSION_API=true`. It requires the guest session feature/configuration and accepts the signed conversation token in `X-Intake-Session`. The endpoint accepts only JSON fields in the intake allowlist, caps the request body at 64 KiB, requires explicit consent, and checks exact Origin before service work. Browser preflight is supported. It uses `CCH_INTAKE_CCH_API_BASE_URL`, `CCH_INTAKE_CCH_USERNAME`, `CCH_INTAKE_CCH_PASSWORD`, and `CCH_INTAKE_OFFICE_CODE`; the URL must use HTTPS. Keep all credentials in a secret store, never in source control.

After consent, the service validates active legacy references and exact customer match. A unique match uses canonical customer name/email/phone; zero or multiple matches are stored as `pending_cs` without creating a ticket. For a unique match, a unique `conversation_id` draft claim prevents concurrent/replayed submissions from issuing a second Add. The `creating` state is reconciled against exact ticket fields after an uncertain upstream response; exactly one match becomes `created`, while zero or multiple matches become `pending_cs`. This is application-level replay protection and best-effort reconciliation, not an atomic idempotency key shared with the legacy API. Do not automatically retry a `pending_cs` result.

The feature remains off by default. Before production, define and enforce a retention/deletion period for consented PII drafts, provision least-privilege DB/API accounts, coordinate JWT key rotation, and configure edge-level rate limiting. Do not enable it until those operational/privacy controls are accepted. Guest intake does not accept attachments; complaint document upload/download use separate gated routes.

### Guest Intake CS Review

`CCH_ENABLE_GUEST_INTAKE_REVIEW_API` gates `GET /api/v1/intake/review/drafts`, `GET /api/v1/intake/review/drafts/{id}`, `GET /api/v1/intake/review/customers/search?q=...`, and `POST /api/v1/intake/review/drafts/{id}/create-ticket`. The reviewer must be the single Call Center role (`3`), at the configured intake office, with `View` on `cchentricus` and `Add` on `cchentri`; account and permissions are revalidated server-side. Draft detail and candidate search are no-store. Customer search requires at least three characters and returns at most 20 candidates.

Ticket creation requires `identity_verified: true`, a pending draft with stored consent, and a selected customer. The profile snapshot is loaded canonically from CCH. Only `Kantor_Tujuan`, `Kantor_Asal_Kiriman`, and `Kantor_Tujuan_Kiriman` are accepted as corrections. A conditional SQL claim moves the draft from `pending_cs` to `creating` and persists the corrected payload before the legacy API call. The technical CCH account is separately checked for `Add`, Call Center role, and configured office. Ticket tables and CCH side effects are still written only by `/api/add/cchentri`.

The draft table has no separate office column, so the current review workflow assumes one configured intake office per shared draft database. Reviewer username, identity attestation, and timestamp are saved under internal `_cs_review` metadata in the draft payload; a separate immutable audit event is not implemented. Before production, define and enforce PII retention/deletion, provision least-privilege DB/API accounts, coordinate JWT key rotation, and configure edge-level rate limiting.

## Test

```powershell
go test ./...
```

An opt-in MariaDB integration test exercises the dashboard SQL and concurrent status transitions against InnoDB. Set `CCH_TEST_MARIADB_DSN` to a dedicated, empty disposable database whose name starts with `cch_be_test_`, then run `go test ./internal/modules/complaints/repository -run '^TestMariaDBDashboardCountsAndStatusTransitionConcurrency$'`. The test refuses other database names and non-empty schemas, creates only fixture tables there, and drops them afterward. Without the variable it is skipped. Never point it at the application `cch` database.

Current packages are intentionally small: `cmd/api` composes the application, `internal/platform` contains process-level configuration and Fiber setup, `internal/modules/health` owns health probes, `internal/modules/authorization` owns permission policy and action checks, and each business domain owns its own service, repository adapters, and HTTP controller under `internal/modules/<domain>/controller`. Complaint workflows live in `complaints`, customer profile search in `customers`, follow-up reads in `followups`, and guest conversation/submission/review in `intake`; controllers do not share a global handler package. These modules are composed only when their opt-in flag and prerequisites are present; all business routes are disabled by default. Multi-role accounts fail closed pending active-role semantics.

The Call Center list, detail, and status-history handlers are implemented and tested. They are registered by `cmd/api` only when the opt-in flag is enabled and its DB/JWT prerequisites pass. Detail uses `View` permission and returns only open tickets visible through origin or exact routed-office membership; inaccessible and unknown IDs share the same 404 response. Customer contact and complaint narrative are included because the legacy CCH view displays them to authorized staff.

`GET /api/v1/complaints/call-center/{id}/status-options` returns only active legacy status choices for an open ticket whose origin office matches the revalidated Call Center office. It requires `View cchentri`, `Add cchentrimas`, role `3`, and matching office/role across both permission checks. For a Call Center at the origin office, the legacy lookup permits `103` and `109`. This endpoint is read-only and does not perform the transition.

`GET /api/v1/complaints/call-center/open/count` is a read-only dashboard count behind `CCH_ENABLE_CALL_CENTER_COMPLAINT_READ_API`. It requires `List cchentri`, role `3`, uses `Status_Akhir <> '109'` with `Kantor_Asal OR exact Semua_Tujuan`, and accepts optional `from`/`to` complaint-date filters. This count predicate is intentionally separate from the open list projection and other dashboard counters.

`GET /api/v1/complaints/call-center/received-open/count` and `/sent-open/count` implement the legacy Dashboard2 `GetJumlahPengaduanTerimaTerbuka` and `GetJumlahPengaduanKirimTerbuka` predicates. Both count `Status_Akhir <> '109'` and accept the same optional complaint-date range. Received uses exact office-token membership in `Semua_Tujuan` only; sent uses `Kantor_Asal = office` only. They do not reuse the combined open-count predicate. Both require `List cchentri`, exactly role `3`, and the current office from database-revalidated account access; they are covered by the existing complaint-read feature flag and return no-store responses.

The role-aware dashboard count routes are `/api/v1/complaints/dashboard/open/count`, `/received-open/count`, `/sent-open/count`, and `/completed/count`. They preserve each legacy predicate separately and allow only one DB-revalidated office role at a time: UPT `1`, UPT Bandara `2`, Call Center `3`, Admin UPT `9`, Regional `10`, Admin Regional `19`, Kantor Pusat `20`, or Admin Pusat `29`. All require `List cchentri`; office scope always comes from the current account. Multi-role accounts and System Administrator remain denied; the latter requires an approved trusted-principal mapping before any global dashboard scope can be exposed. These routes share the default-off complaint read registrar.

The same dashboard group now includes paginated `GET /api/v1/complaints/dashboard/received-open` and `/sent-open` detail lists with optional `from`/`to` filters. Received uses only exact membership in `Semua_Tujuan`; sent uses only `Kantor_Asal`; both require `Status_Akhir <> '109'`. They use the existing minimal complaint summary projection and the same single-role, `List cchentri`, trusted-office policy as the dashboard counts.

`GET /api/v1/complaints/reports/received-open` implements a bounded detail slice of legacy `CchRincianTerimaTerbuka`. It requires `from` and `to`, accepts optional `product_code` (`999` means all products), and uses the authenticated account's current office rather than a caller-selected office. The query requires an initial distribution row (`cchentridet.Status_Update = '101'`) for that exact target office, a non-109 parent and latest history status, and returns the latest status/office/time plus elapsed seconds. It requires `List` on `cchentri`, `cchentridet`, and `cchentrimas` with consistent office/role/report-to across ACL checks. The office scope is intentionally narrower than the legacy report's free-form regional/office selector; route remains default-off and no contact PII is returned.

`GET /api/v1/complaints/reports/sent-open` mirrors legacy `CchRincianKirimTerbuka`: it requires `from` and `to`, accepts the same optional `product_code`, and scopes by `cchentri.Kantor_Asal` equal to the authenticated account's current office only. It also requires an initial distribution row (`cchentridet.Status_Update = '101'`), resolves the latest `cchentrimas` row deterministically, and returns only tickets whose latest history status is not `109` (the legacy page applies the open filter against the latest status, not the parent `Status_Akhir`). It requires `List` on `cchentri`, `cchentridet`, and `cchentrimas` with consistent office/role/report-to across ACL checks, returns a bounded projection without customer contact fields, uses the same `private, no-store` policy, and remains behind the default-off complaint read flag.

`GET /api/v1/complaints/reports/received-open/duration-buckets` returns the five age buckets (`day_zero`, `day_one`, `day_two`, `day_three`, `day_four_plus`), counts, two-decimal percentages, and total for open received tickets in the authenticated office. It requires `from` and `to`, accepts the same optional `product_code`, and uses the initial status-101 target distribution plus exact membership in `Semua_Tujuan`. Age is calendar-day difference from `Tanggal_Tambah` to the MariaDB current date. It requires `List` on `cchentri` and `cchentridet`; an empty result returns zero counts and percentages. This is a narrow office-scoped slice, not the legacy regional selector/export.

`GET /api/v1/complaints/reports/sent-open/duration-buckets` is the sent counterpart with the same five-bucket response shape. It requires `from` and `to`, accepts the same optional `product_code`, and follows the sent-open-report policy: `cchentri.Kantor_Asal` equality, initial status-101 distribution, deterministic latest `cchentrimas` row, and latest history status not `109` (the parent `Status_Akhir` is not filtered). Because the open filter reads the history row, it requires `List` on `cchentri`, `cchentridet`, and `cchentrimas` with consistent office/role/report-to, and stays behind the default-off complaint read flag.

`GET /api/v1/complaints/reports/sent-summary` implements the legacy `CchRekapKirim*` rekapitulasi as a grouped, paginated summary. It requires `from` and `to`, accepts optional `product_code` (`999` = all) and `regional` (`0`/empty = all, otherwise a regional office code), and groups sent complaints by origin office. Each row reports total, completed (`109`), open, responded, and unresponded (`101`) plus two-decimal percentages; the legacy MPC-Jakarta cap is preserved by deriving open from the clamped completed count. It requires `List` on `cchentri` and `cch_kantor` with consistent office/role/report-to, returns no contact PII, and is `private, no-store`. Regional detail links and the Excel-HTML export remain unported.

`GET /api/v1/complaints/reports/received-summary` is the received counterpart (`CchRekapTerima*`). It groups by target office from the initial distribution (`cchentridet.Kantor_Tujuan_Update` with `Status_Update = '101'`) and reports the same five-way breakdown (total, completed `109`, open, responded, unresponded `101`) with two-decimal percentages and the MPC-Jakarta clamp. Filters: required `from`/`to`, optional `product_code` (`999` = all), `regional` (`0`/empty = all), and `hanya_tujuan` (`on`/`1`/`true` narrows to `e.Kantor_Tujuan = u.Kantor_Tujuan_Update`). It requires `List` on `cchentri`, `cchentridet`, and `cch_kantor`, returns no contact PII, and is `private, no-store`.

The per-product detail routes `sent-per-shipment`, `sent-per-problem`, `received-per-shipment`, and `received-per-problem` under `/api/v1/complaints/reports/` mirror legacy `CchRekapKirimJenis*`/`CchRekapTerimaJenis*`. Each returns `{code, label, count, percent}` rows plus top-level `total`/coverage `percent`, bounded-paginated and `private, no-store`. Sent variants scope by origin office; received variants scope by target office distribution (`Status_Update = '101'`) and honor `hanya_tujuan`/`regional`; all accept required `from`/`to` and optional `product_code`/`regional`. ACL: `List` on `cchentri` + `cch_kantor` for sent, plus `cchentridet` for received.

### Customer Profile CRUD

`CCH_ENABLE_CUSTOMER_PROFILE_API` gates `GET/POST /api/v1/customers`, `GET/PUT/DELETE /api/v1/customers/{id}` and defaults to `false`. Every method requires its matching `List`, `View`, `Add`, `Edit`, or `Delete` ACL action on `cchentricus`; all reads and writes are restricted to the caller's DB-revalidated office (`Kantor_Tambah`). ### Complaint Type Master CRUD

`CCH_ENABLE_COMPLAINT_TYPE_MASTER_API` gates `GET/POST /api/v1/masters/complaint-types`, `GET/PUT/DELETE /api/v1/masters/complaint-types/{code}` and defaults to `false`. Each operation requires its matching CCH table action on `cch_jenis_pengaduan`: `List`, `View`, `Add`, `Edit`, or `Delete`; account and permission data are revalidated from CCH. Codes follow the signed TINYINT range and are immutable after creation; descriptions are nullable and limited to 50 characters; active state maps to legacy `Y/N`. `DELETE` is a repeatable soft-deactivation (`Status_Aktif = 'N'`) to preserve historical ticket references. Duplicate codes return `409`; invalid payloads return `400`; responses are private/no-store. Default user-level ACL entries are deny, so explicitly provision action permissions before enabling this flag. CRUD is tested with mocks; no live master data has been changed.

`CCH_ENABLE_COMPLAINT_SOURCE_MASTER_API` gates `GET/POST /api/v1/masters/complaint-sources`, `GET/PUT/DELETE /api/v1/masters/complaint-sources/{id}` and defaults to `false`. Actions require the matching `List`, `View`, `Add`, `Edit`, or `Delete` permission on `cch_sumber_pengaduan`. `name` is required and limited to 100 characters; `active` maps to `Apakah_Aktif` (`Y/N`); the server owns the auto-increment ID and add/update timestamps. DELETE soft-deactivates the source to retain historical ticket references. Legacy has no unique source-name constraint, so Go does not invent one. Explicitly provision ACL before enabling; no live master rows were changed.

`CCH_ENABLE_SHIPPING_SERVICE_MASTER_API` gates `GET/POST /api/v1/masters/shipping-services`, `GET/PUT/DELETE /api/v1/masters/shipping-services/{code}` and defaults to `false`. Each operation checks its matching `List`, `View`, `Add`, `Edit`, or `Delete` action on `cch_jenis_layanan`. Code follows legacy `CHAR(3)` and is immutable on update; description is capped at 25 characters; tracking URL is required and capped at 255; `active` maps to `Status_Aktif` (`Y/N`); `Waktu_Akhir` is server-managed. DELETE soft-deactivates. The URL is stored as master data and is never fetched by BE. The existing intake lookup continues listing all services, matching its legacy no-active-filter behavior.

`GET /api/v1/complaints/call-center/open/export` returns the existing open-ticket projection as CSV, bounded by the standard pagination limit (maximum 100 rows). It requires both `List` and `Export` on `cchentri`, exactly role `3`, and uses the same trusted office/status-routing predicate as the open list. The CSV omits customer contact fields, uses fixed columns, neutralizes spreadsheet formula-like values, and is sent as `private, no-store` attachment. It shares the default-off complaint read gate.

### Handling Status Master CRUD

`CCH_ENABLE_HANDLING_STATUS_MASTER_API` gates `GET/POST /api/v1/masters/handling-statuses`, `GET/PUT/DELETE /api/v1/masters/handling-statuses/{code}` and defaults to `false`. Each operation requires its matching `List`, `View`, `Add`, `Edit`, or `Delete` action on `cch_jenis_penanganan`. Codes are exactly three characters and immutable; descriptions are required and limited to 50 characters; `active` maps to legacy `Aktif` (`Y/N`). DELETE sets `Aktif='N'` instead of removing the row because status codes are referenced by `cchentri.Status_Akhir` and `cchentrimas.Status_Update`; history labels remain resolvable. This master API does not widen the supported status-transition matrix. Acceptance tests are included but have not been run per the current testing schedule.

### Office Master CRUD

`CCH_ENABLE_OFFICE_MASTER_API` gates `GET/POST /api/v1/masters/offices`, `GET/PUT/DELETE /api/v1/masters/offices/{code}`, and `GET /api/v1/masters/offices/options`; it defaults to `false`. CRUD actions require the matching `List`, `View`, `Add`, `Edit`, or `Delete` ACL on `cch_kantor`; the options route requires `Lookup`. The office code is immutable and limited to seven ASCII characters. Required text fields match the legacy limits: name 50, abbreviation 10, type 10, and regional code 5 characters; input must be representable by the legacy `latin1` columns. `Jenis` options mirror distinct values already present in `cch_kantor`; regional options mirror the legacy active `KP`/`Divre` filter. Create/update reject unknown types and inactive/non-regional parent codes. DELETE sets `Apakah_Aktif='N'`, preserving office rows referenced by users and historical ticket routing. There are no legacy row-hook side effects or audit columns. Tests are included but not run per the current testing schedule.

### Regional Office Administration

`CCH_ENABLE_REGIONAL_ADMIN_API` gates `GET /api/v1/admin/regional-offices`, `GET /api/v1/admin/regional-offices/{code}`, `GET /api/v1/admin/regional-offices/options`, and `PUT /api/v1/admin/regional-offices/{code}`; it defaults to `false`. Legacy `CchRegionalController` exposes only list/view/edit and is protected by `PermissionMiddleware`. `cch_regional` is an updatable view over `cch_kantor` restricted to `Jenis IN ('Divre','KP')`, ordered by abbreviation. List/View/Edit require the corresponding action on `cch_regional`; lookup options require `Lookup cch_kantor`, matching the legacy lookup source. Update accepts the legacy edit fields (office name, abbreviation, type, regional code, active); the office code in the URL is immutable in Go to protect user/ticket references. The repository locks and confirms the source row is still a KP/Divre office, locks the assigned parent office, then updates the base `cch_kantor` row in one transaction. Regional code must exist and fit the underlying `VARCHAR(5)`; text limits/latin1 representability match `cch_kantor`. No Add/Delete routes are exposed, matching legacy. This endpoint overlaps the broader Office Master update surface and the legacy PHP writer on the same rows; row locks serialize DB transactions but do not prevent stale last-writer-wins updates across clients, so keep default-off until ownership/rollout coordination is approved. Responses are private/no-store. Acceptance tests use sqlmock; no live office data was read or changed.

### CS Officer Roster and Status

`CCH_ENABLE_CS_OFFICER_STATUS_API` gates read-only `GET /api/v1/admin/cs-officers` and `GET /api/v1/admin/cs-officers/{username}`; it defaults to `false`. Legacy `CchCsOfficerController` exposes only list/view behind `PermissionMiddleware`. The owner is the `cch_cs_officer` view over `cch_users` with its inherent `Display_In_CS_List='Y'` predicate; it projects report-to (`Regional`), office, username, full name, `Current_Status` (`Login`/`Logout`), email, phone, and login/logout timestamps. Legacy `recordsetSelecting()` adds no extra office/role scope. The Go API therefore requires `List`/`View` ACL on `cch_cs_officer`, does not invent office scoping, and returns the legacy projection with private/no-store headers because it includes staff contact PII. List supports exact regional/office/status filters, username/name prefix search, and bounded pagination (default 25, max 100). Status is the current CS login/logout status, not a complaint status; no update endpoint is provided because legacy routes/model expose this as a view. Acceptance tests use sqlmock/stubs only; no user rows were read.

### User-Level Catalog

`CCH_ENABLE_USER_LEVEL_CATALOG_API` defaults to `false` and gates read-only `GET /api/v1/admin/user-levels` and `GET /api/v1/admin/user-levels/{id}`. Legacy `/cchuserlevelslist` and `/cchuserlevelsview` routes use `PermissionMiddleware`; `cch_userlevels` stores the integer `User_Level_ID` and required `User_Level_Name`, and its row hooks add no write side effects. List and detail require their respective `List` and `View` table actions on `cch_userlevels`. The API returns only those two columns with bounded pagination (default 25, maximum 100), accepts legacy signed integer IDs, and uses private/no-store responses. It does not read or expose `cch_userlevelpermissions`; user, role, and permission mutations are out of scope because user assignments and ACL rows reference these IDs and require a separately approved write policy. ### Call Center Status Mutation

`POST /api/v1/complaints/call-center/{id}/status` is a separate default-off route controlled by `CCH_ENABLE_CALL_CENTER_STATUS_WRITE_API=true`. Startup also requires `CCH_LEGACY_STATUS_WRITES_FENCED=true`, a configured MySQL connection, a valid staff JWT verifier, and the table from `migrations/0001_create_status_transition_idempotency.sql`. Apply that additive migration before enabling the route. The fence setting is an operator assertion, not runtime proof: block the legacy `/api/add/cchentrimas` status-write path at the deployment edge and verify it cannot mutate status while Go is enabled. Never run both writers concurrently.

The current supported policy is Call Center role `3` at the ticket's origin office, on an open ticket. It accepts an expected current status other than `109` and an active next status of `103` or `109`, matching the legacy lookup options and row-insert guards for this role. Other roles and status transitions are not implemented. The body allowlist is `expected_status_code`, `status_code`, and `description`; `Idempotency-Key` is a required 16-128 character ASCII header. The response is `201` for a new transition and `200` for an exact replay. Invalid input is `400`, inaccessible/ineligible tickets are `404`, stale status or reused key with a different payload is `409`; responses are no-store.

One InnoDB transaction claims the idempotency key and writes `cchentridet` distribution rows, `cchentrimas` history, the `cchentri` status snapshot, and duration. Parent and active status rows are locked/revalidated; stale expected status and closed tickets roll back. The idempotency table is append-only by design so retries remain recognizable; define monitoring and backup for its growth. Automated tests use sqlmock only. No migration has been applied and no live MariaDB/CCH write has been tested, so keep the route disabled until an isolated integration test and rollout review pass.

## Module Boundaries

- `cmd/api` is the composition root: load configuration, open infrastructure dependencies, register modules, and start the server.
- `internal/platform` owns cross-cutting infrastructure such as Fiber setup, request IDs, error responses, configuration, and database connection management.
- `internal/modules/<domain>` owns one business capability. Keep HTTP handlers at the transport edge, business rules in application/domain code, and SQL in repository adapters.
- Domain and application packages must not depend on Fiber or concrete SQL driver types. Inject narrow interfaces at module boundaries.
- Business endpoints are versioned under `/api/v1`. Liveness/readiness probes stay at `/healthz` and `/readyz`.
- Ticket writes require an explicitly approved ownership boundary, status/office policy, idempotency, transaction behavior, and deployment fence. The Call Center status writer is the first narrow implementation; it remains default-off.

The Go Call Center status writer does not call the generic legacy Add route. It writes the history, office distribution, parent snapshot, and duration in one explicit SQL transaction, with durable idempotency in a Go-owned table. The route is separately gated and refuses startup unless the operator asserts the legacy status writer is fenced. This does not prove deployment fencing or legacy JWT key rotation; those controls and an isolated MariaDB failure-injection test remain rollout prerequisites.

`cmd/api` is currently the development composition root for shared HTTP infrastructure. It is not a mandate to place every future CCH domain in one deployable binary. If a domain needs independent deployment, add a separate `cmd/<service>` entrypoint and compose only that service's modules.

## HTTP Contract

- `GET /api/v1/` returns service name and API version metadata.
- Every request receives a generated `X-Request-ID`; API error responses include the same ID for support correlation.
- Errors use `{ "error": { "code": "...", "message": "..." }, "request_id": "..." }`. Internal errors do not expose database or stack details.
- Domain handlers will be registered under `/api/v1` by their own module. Health probes remain outside the versioned business API.
