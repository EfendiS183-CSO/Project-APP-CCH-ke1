# CCH Domain Workflow Notes

**Purpose:** Record verified behavior from the existing Customer Complaint Handling (CCH) application before implementing domain behavior in Go. This is a working technical note, not an approved replacement specification.

## Source-of-Truth Rule

The PHP application and MySQL schema are the current behavior baseline. BRD/SRS/FSD Enterprise documents include target-state behavior that does not always match the running application. Preserve verified business rules unless a product owner approves a change. MySQL remains the selected database; PostgreSQL migration is out of scope for now.

## Complaint Lifecycle

1. `cchentri` is the complaint/ticket aggregate root in the legacy schema. It stores customer and shipment snapshots, current status, current status office, and status timestamp.
2. Ticket creation initializes status `101` (ENTRI), server-side timestamps and actor/office values, plus routing/distribution values.
3. The creation hook writes the initial `cchentrimas` history record, one or more `cchentridet` office-distribution records, and the `cchmas` case-summary record. The CCH API add path wraps the ticket insert and these hook side effects in a DB transaction.
4. Subsequent status changes are appended to `cchentrimas`; `cchentridet` records offices associated with that update. The history hook updates the current-state snapshot on `cchentri` and calculates `Durasi_Antar_Status` from adjacent history timestamps.
5. Status `109` (SELESAI) blocks further status-history inserts. `cchselesai` is a view of tickets at status 109, not a separate archive table.

Status codes confirmed from the application/database notes: `101` ENTRI, `102` RESPON, `103` KONFIRMASI, `104` RESOLVED, and `109` SELESAI. Codes `105` and `106` have appeared in data, but their approved labels and transition rules have not been established here. Do not hard-code a complete state machine until the master status table and product rules are reconciled.

**Consistency warning:** API ticket creation is explicitly transaction-wrapped around row insertion and side effects. The generated status-add flow starts its transaction conditionally based on detail-table context, while office-distribution inserts occur in its pre-insert hook. Verify transaction coverage and rollback behavior before exposing status mutation through a new Go endpoint.

## Follow-up

- `cchfu` records follow-up plan and realization against the composite key `(ID_Pengaduan, Kantor, Status)`.
- Plan fields include planned date, assigned staff, and notes; realization fields include actual date, staff, and outcome.
- `cchfual` exposes all follow-ups. `cchfuhi` exposes items planned for today that have not been realized.
- The base `Cchfu` model hooks do not add extra workflow behavior. Authorization and office scoping must still be verified in the page/API path before reproducing this feature.
- The opt-in Go Call Center subresource lists follow-ups only through an open parent complaint already scoped by exact origin/`Semua_Tujuan` membership. It requires `View` on `cchentri`, `List` on `cchfual`, a single role ID `3`, and matching current office/role from both ACL reads. It intentionally does not filter `cchfual.Kantor`, matching the legacy Call Center master/detail behavior that exposes related offices' follow-ups for the selected complaint. A visible complaint with no follow-up rows returns an empty list; missing or out-of-scope parent tickets are hidden as 404. Assigned staff fields are omitted like the legacy list. This is read-only; wider role scopes remain unimplemented.
- The Go Call Center office-list endpoint reads the base `cchfu` table and requires `List` permission plus exactly role ID `3`. Its office predicate is `cchfu.Kantor =` the current DB-revalidated account office; request-supplied office values are ignored. It returns a bounded projection and pagination. This matches the legacy `Cchfu::recordsetSelecting()` office filter. It is distinct from the `cchfual` related-office detail and the `cchfuhi` due-today view; their broader filters are not reused.
- `GET /api/v1/follow-ups/call-center/office/due-today` reads the legacy `cchfuhi` view, which defines due today using the database date and `Tanggal_Realisasi IS NULL`. Go additionally requires `List` on `cchfuhi`, exactly role ID `3`, and filters to the current DB-revalidated office with an exact `Kantor = ?` predicate. Pagination is bounded; office supplied by the caller is ignored. This endpoint is intentionally narrower than the legacy Call Center list, which can expose related offices when an explicit search filter is supplied.
- `POST /api/v1/complaints/call-center/{id}/follow-ups` creates one plan row behind independent flag `CCH_ENABLE_CALL_CENTER_FOLLOWUP_PLAN_API` (default false). It requires `View cchentri`, `Add cchfu`, exactly role `3`, matching office/report-to/role across ACL reads, an open parent visible by origin or exact target-office membership, and an existing `cchfust` code. Only status, planned timestamp, and notes are client supplied. Complaint ID comes from the path; `Kantor` and `Petugas_Rencana` come from revalidated access, and realization fields are NULL. One InnoDB transaction locks the parent, validates the status reference, and inserts into `cchfu`; the composite primary key maps duplicates to `409`. SQL/service/HTTP/route tests use mocks, with no live DB write.
- `POST /api/v1/complaints/call-center/{id}/follow-ups/{status}/realize` records a realization behind independent flag `CCH_ENABLE_CALL_CENTER_FOLLOWUP_REALIZE_API` (default false). It requires `Edit cchfu` and exactly role `3`; its transaction locks the existing `(ID_Pengaduan, Kantor, Status)` row using the DB-revalidated caller office. Only the outcome is accepted from the client; realization timestamp and actor are server-owned. A retry with the same actor and same outcome returns the persisted result; changed actor/outcome conflicts. Missing or another-office rows are hidden as 404. Wider role scopes remain unsupported. SQL/service/HTTP/route tests use mocks; no live DB write.
- `PUT /api/v1/complaints/call-center/{id}/follow-ups/{status}` edits an unrealized plan behind `CCH_ENABLE_CALL_CENTER_FOLLOWUP_EDIT_API`; `DELETE /api/v1/complaints/call-center/{id}/follow-ups/{status}` cancels one behind `CCH_ENABLE_CALL_CENTER_FOLLOWUP_CANCEL_API`. Both require `View cchentri`, the corresponding `Edit`/`Delete` action on `cchfu`, role `3`, and matching office/report-to. They lock the row transactionally, reject realized plans with `409`, and hide missing/closed/out-of-scope rows as `404`.

## Evidence Documents

- `cchentridok` attaches one or more files to a complaint history and document type. Its key includes complaint, history, and document type.
- The add hook checks that the current office matches the origin office of the selected history, creates a path under `attachments/{office}/{complaint}/`, and derives a stored filename from history, office, document type, sequence, and extension.
- Legacy upload-folder creation uses permissive `0777` permissions. Do not copy that implementation into the new services; define storage location, authorization, file validation, and access controls separately.
- The inspected PHP global upload settings allow `gif,jpg,jpeg,bmp,png,doc,docx,xls,xlsx,pdf,zip`, max 2,000,000 bytes per file, and no file-count cap. The relative destination is `files/` under the app root; this does not establish that deployment prevents direct static access. Go now has a private storage root, MIME/extension and size validation, ClamAV ingestion, metadata persistence, and verified binary download behind independent default-off flags. Retention/deletion, production scanning deployment, backup/recovery, and static-serving fence still remain. Do not inherit the legacy extension list or `0777` directory mode by default.
- `GET /api/v1/complaints/call-center/{id}/documents` is a metadata-only read behind independent flag `CCH_ENABLE_CALL_CENTER_DOCUMENT_METADATA_API` (default false). It requires `View cchentri`, `List cchentridok`, exactly role `3`, matching office/report-to/role across authorization reads, and an open parent scoped by origin or exact `Semua_Tujuan`. The query joins metadata to an existing history row, uses bounded pagination, and returns document type, history ID, upload office, added time, and file count. It deliberately omits `Folder`, stored file names, and binary content. Empty documents on a visible ticket return `[]`; missing/out-of-scope/closed parent is 404. This endpoint is not a download/upload contract.

- `GET /api/v1/complaints/call-center/{id}/documents/:documentId/preview` (flag `CCH_ENABLE_CALL_CENTER_DOCUMENT_PREVIEW_API`, default false) serves the same verified binary content as download with `Content-Disposition: inline`, `private, no-store`, and `X-Content-Type-Options: nosniff`. It reuses the download service, so SHA-256, size-limit, and media-type verification all apply before bytes leave the private store. Enrollment requires `View cchentri`, `List cchentridok`, exactly role `3`, a consistent revalidated office/report-to, an open visible parent, and a 32-hex document ID. Missing/out-of-scope/closed subjects return `404`, invalid input `400`. The legacy `CchentridokPreview` web route renders metadata HTML, so the Go binary preview is a deliberate, documented difference rather than a parity copy.
- `DELETE /api/v1/complaints/call-center/{id}/documents/:documentId` (flag `CCH_ENABLE_CALL_CENTER_DOCUMENT_DELETE_API`, default false) removes one document from `cch_be_document_files`. It requires `View cchentri`, `Delete cchentridok`, exactly role `3`, and a matching revalidated office/report-to. A single transaction locks the visible open parent and the metadata row with `FOR UPDATE`; the row must also have `office_code` equal to the caller's trusted office, otherwise `409` (a document uploaded by another office cannot be deleted from here). Missing/out-of-scope rows map to `404`, invalid input to `400`, success to `204`. After commit the private-store object is deleted best-effort; the metadata row is the source of truth, so a transient storage failure never blocks the deletion. This intentionally does not touch legacy `cchentridok` rows or `attachments/` paths; those remain under the PHP runtime.

## Authorization and Integration Boundaries

- Legacy web routes generally pass through `PermissionMiddleware`; access is also scoped by office/role in model/page logic. Authentication alone does not imply access to every complaint.
- The legacy API accepts its configured auth header (`X-Authorization` in the inspected development config), strips an optional `Bearer` prefix, and validates the JWT signature and time claims before using its nested `security` payload.
- The observed JWT `security` payload contains `username`, `userid`, `parentuserid`, `userlevelid`, and an allowed-permission mask. In the inspected CCH configuration, `USER_ID_FIELD_NAME` maps `userid` to `cch_users.Office`, and `PARENT_USER_ID_FIELD_NAME` maps `parentuserid` to `cch_users.Report_To`.
- These office values are custom claims inside the signed token, not separate `Office`/`Report_To` fields. Go may use them only after verifying signature, algorithm, issuer, and expiry. The legacy security layer reloads user-level permission rows from the database and intersects them with the token's allowed-permission mask.
- CCH stores table-level permissions in `cch_userlevelpermissions`. Permission masks from multiple user levels are ORed; the token mask is intersected only when it is greater than zero. System Administrator level `-1` starts with `ALLOW_ALL` (`524287` in the inspected constants), but a positive token mask still restricts it. Permission bits include Add `1`, Delete `2`, Edit `4`, List `8`, Admin `16`, View `32`, Search `64`, Import `128`, Lookup `256`, Push `512`, and Export `1024`; export-format bits continue from Print `2048` through Email `262144`.
- The ACL `Table_Name` key is not just a raw table name: legacy code compares it with `PROJECT_ID + table variable` (the project GUID followed by names such as `cchentri`). Preserve that exact key format in any compatibility repository and test it against approved metadata.
- System Administrator is a special legacy principal validated by a separate configured admin identity; do not grant Go access merely because an untrusted request supplies level `-1`. Until a safe mapping is approved, deny this principal in new business APIs.
- Table/action permission does not replace office data scoping. An authorized `View` permission must still be combined with the correct office/role filter for each CCH use case.
- Signed office claims can become stale if an account is moved, locked, or deactivated before token expiry. For sensitive operations, revalidate current account status and office/role against trusted CCH data or use an explicitly approved short revocation policy. A role/level claim alone is not sufficient for authorization.
- Go should accept bearer credentials only from the configured header; do not copy legacy query-string or cookie fallback behavior into new API clients.
- Signing keys are statically configured in tracked legacy configuration. Treat those keys as exposed: do not copy them into Go source. Before Go accepts legacy-issued tokens, rotate the signing key and move issuer/verifier configuration to a coordinated secret source.
- The new Go backend must own authorization decisions for its endpoints and enforce office scope server-side. The React client and AI Engine are not trusted authorities.
- The AI Engine may return structured suggestions, but Go validates them and owns persisted business actions.
- Do not let Go or FastAPI write directly to legacy ticket tables until data ownership, transaction boundaries, and compatibility are designed. Prefer the existing CCH API or an explicitly versioned adapter during transition.

## Legacy Complaint List Visibility

These are observed PHP Maker behaviors, not yet an approved Go API policy:

- `/cchentrilist` passes through `PermissionMiddleware`; `Cchentri::recordsetSelecting()` adds row filters after the page permission check.
- For non-admin users, an empty list filter is replaced with `0=101`, which returns no rows by default.
- For ordinary roles with a non-empty filter, visible rows are matched by `Kantor_Asal = current office`, `Kantor_Tujuan = current office`, or `Kantor_Tembusan LIKE '%current office%'`.
- Role helpers compare the active user-level ID with fixed values: UPT `1`, UPT Bandara `2`, Call Center `3`, Admin UPT `9`, Regional `10`, Admin Regional `19`, Kantor Pusat `20`, and Admin Pusat `29`. For this special group, the list hook adds `Semua_Tujuan LIKE '%current office%' OR Kantor_Asal = current office` only when the incoming filter text contains `Status_Akhir <> '109'`. Other query shapes therefore do not get that same scope from this hook.
- `IsAdmin()` bypasses the list hook's office filters. In PHPMaker it may be true due to level `-1`, office `-1`, or the table's Admin permission; do not reproduce this as unrestricted access without a separately approved, trusted admin mapping.
- Dashboard use cases are not the same policy: open-ticket counts use `Semua_Tujuan` or origin; received-open counts use `Semua_Tujuan`; sent-open counts use origin; completed counts use the `cchselesai` view and a separate scope. Do not implement one generic office filter for all these workflows.
- `Semua_Tujuan` is generated from routed offices, including destination/regional offices and central office. Legacy filters use substring `LIKE`, which can match partial office codes; a new Go implementation should use exact token membership for comma-delimited office codes if that contract is approved.

The Go backend has an `AccessService` for table/action authorization, `complaints.ComplaintRouting` for exact office membership across legacy routing fields, and `complaints/repository.MySQLComplaintRepository` for bounded read-only list/detail/history queries. List requires CCH `List` permission on `cchentri`; detail requires `View`; history requires `List` on both `cchentri` and `cchentrimas`. These Call Center use cases require a single role ID `3` and the office revalidated from CCH. List/detail/history are limited to open parents visible through origin or exact `Semua_Tujuan` membership; missing and out-of-scope detail IDs share the same 404. History is returned chronologically with legacy status description, update office, narrative, actor, and duration. These reads do not grant status mutation or closed-ticket access. `cmd/api` registers the handlers only when the default-off read API flag and DB/JWT prerequisites are satisfied; other roles/workflows still need separate policies and acceptance tests.

## Call Center Ticket Detail

`GET /api/v1/complaints/call-center/open/count` follows the legacy `GetJumlahSemuaPengaduanTerbuka` predicate: non-109 `cchentri` rows visible through `Kantor_Asal` or exact `Semua_Tujuan` membership, with an optional `Tanggal_Pengaduan` range. This is a dashboard count policy, not a replacement for the open list policy.

`GET /api/v1/complaints/call-center/received-open/count` and `/sent-open/count` map to the legacy Dashboard2 functions `GetJumlahPengaduanTerimaTerbuka` and `GetJumlahPengaduanKirimTerbuka`. Both filter `Status_Akhir <> '109'` and optional `Tanggal_Pengaduan` bounds; received uses only exact office membership in `Semua_Tujuan`, while sent uses only `Kantor_Asal = office`. They are intentionally not aliases for the combined open count. Go restricts these endpoints to the single Call Center role and the DB-revalidated account office, and uses exact CSV token matching rather than the legacy substring `LIKE`.

The separate role-aware dashboard routes expose open, received-open, sent-open, and completed counts using their individually traced predicates. They allow one current office role from IDs `1`, `2`, `3`, `9`, `10`, `19`, `20`, and `29`, require `List cchentri`, and always derive office from database-revalidated access. Multi-role accounts remain unsupported because there is no approved active-role selection contract. System Administrator remains denied because the existing trusted-principal mapping is not available to Go; do not turn the legacy global count branch into unscoped access by accepting a `-1` claim.

The same dashboard group exposes paginated received-open and sent-open detail lists with optional complaint-date bounds. Both require open status (`Status_Akhir <> '109'`); received filters only exact `Semua_Tujuan` membership and sent only exact origin office. They use the bounded complaint summary projection, not the customer-contact detail DTO, and share the role/action/office policy described above.

`GET /api/v1/complaints/reports/received-open` is a separate detail report based on legacy `CchRincianTerimaTerbuka`. It requires a date range and accepts an optional shipment product code (`999` is normalized to all products). Its rows originate from `cchentridet` distributions with `Status_Update = '101'` and `Kantor_Tujuan_Update` exactly equal to the DB-revalidated account office. It joins the parent ticket and deterministically chooses the latest `cchentrimas` row by update timestamp then history ID; both parent and latest history must remain non-109. The response includes routing offices, shipment number/type, complaint-created time, latest status/description/office/time, and elapsed seconds, without customer contact fields. It requires `List` on `cchentri`, `cchentridet`, and `cchentrimas`, with matching office, role, and report-to across revalidation. Unlike the legacy selector, Go currently does not allow a caller to choose another office or regional scope; this is an intentional narrow first slice.

`GET /api/v1/complaints/reports/sent-open` mirrors legacy `CchRincianKirimTerbuka`, which is a thin custom page whose real source query is in `views/CchRincianKirimTerbuka.php`. That query selects distinct tickets from `cchentridet` joined to `cchentri` where `cchentri.Kantor_Asal` equals the selected office, `cchentridet.Status_Update = '101'`, `cchentri.Tanggal_Tambah` is within the report range, and an optional product filter on `cchentri.Jenis_Kiriman`; it then resolves each ticket's latest `cchentrimas` row and only displays rows whose latest history status is not `109`. Unlike the received report, the legacy sent query does not filter the parent `Status_Akhir`; open-ness is decided against the latest history status. The Go slice reproduces that: origin-office-only scope, initial status-101 distribution, deterministic latest-history subquery ordered by update timestamp then history ID, latest history not `109`, bounded pagination, and no customer contact fields. It requires `List` on `cchentri`, `cchentridet`, and `cchentrimas` with consistent office/role/report-to, and stays behind the default-off complaint read flag. Regional/office selection and Excel export from the legacy page remain unported.

`GET /api/v1/complaints/reports/received-open/duration-buckets` aggregates open received tickets for the authenticated office into calendar-age buckets `0`, `1`, `2`, `3`, and `4+` days from `Tanggal_Tambah` to MariaDB `CURRENT_DATE`. The eligible parent set uses the initial target distribution (`cchentridet.Status_Update = '101'`), exact target-office equality, exact `Semua_Tujuan` membership, non-109 parent status, date bounds, and optional product code. It requires `List` on `cchentri` and `cchentridet`; response includes bucket counts, percentages rounded to two decimals, and total. This avoids the legacy report's substring office `LIKE` and its `ORDER BY Status_Update DESC` latest-state ambiguity. It remains narrower than the legacy regional/product selector; regional grouping, its detail links, and Excel export are not implemented.

`GET /api/v1/complaints/reports/received-summary` is the rekapitulasi terima (`CchRekapTerima*` family), the received counterpart of `sent-summary`. It groups by target office (`cchentridet.Kantor_Tujuan_Update` with `Status_Update = '101'`), counts distinct tickets, and uses the same five-way breakdown as sent summary: total, completed (`Status_Akhir = '109'`), open, responded, and unresponded (unresponded = latest active distribution status for that target is `'101'`), with the MPC-Jakarta clamp. Filters are `from`/`to` (required), optional `product_code` (`999` = all), `regional` (`0`/empty = all; else `cch_kantor.Regional = ? OR cch_kantor.Kode_Kantor = ?`), and the legacy `hanya_tujuan` switch (`on`/`1`/`true`) which narrows to `e.Kantor_Tujuan = u.Kantor_Tujuan_Update`. The Go query uses exact ticket-distribution matching and deterministic aggregation instead of the legacy per-row queries and substring `Semua_Tujuan` `LIKE`. It requires `List` on `cchentri`, `cchentridet`, and `cch_kantor` with consistent office/role/report-to, returns only office aggregates without contact PII, is bounded-paginated, and `private, no-store`. Regional detail links and Excel-HTML export remain unported.

The per-product breakdowns `GET /api/v1/complaints/reports/sent-per-shipment`, `sent-per-problem`, `received-per-shipment`, and `received-per-problem` mirror legacy `CchRekapKirimJenisKiriman`, `CchRekapKirimJenisMasalah`, `CchRekapTerimaJenisKiriman`, and `CchRekapTerimaJenisMasalah`. Each returns `{code, label, count, percent}` rows (joined to `cch_jenis_layanan` for shipment kinds and `cch_jenis_pengaduan` for problem kinds, active only for problem labels) plus a top-level `total` and coverage percentage, bounded-paginated and `private, no-store`. Sent variants scope by origin office with optional `product_code`/`regional`; received variants scope by the target-office distribution (`cchentridet.Status_Update = '101'`) with optional `regional`/`hanya_tujuan`/`product_code`, all with required `from`/`to`. Sent requires `List` on `cchentri` + `cch_kantor`; received adds `cchentridet`. Percentages are computed against the returned grand total rather than the legacy cross-check against a separate overall query. Excel-HTML export and the per-row regional detail links remain unported.

`GET /api/v1/complaints/reports/sent-open/duration-buckets` is the sent counterpart and mirrors the same five calendar-age buckets for open sent tickets of the authenticated office. It follows the sent-open-report policy: origin-office equality (`cchentri.Kantor_Asal`), initial `cchentridet.Status_Update = '101'` distribution, deterministic latest `cchentrimas` row, latest history status not `109` (the parent `Status_Akhir` is not filtered, matching the legacy sent pages), date bounds, and optional product code. Unlike the received buckets it therefore requires `List` on `cchentri`, `cchentridet`, and `cchentrimas` with consistent office/role/report-to. The response shape is identical to received: `day_zero`..`day_four_plus` counts, rounded percentages, and total. The legacy sent duration pages (`CchRincianKirimDurasiMasihTerbuka`, `BelumRespon`, `SudahRespon`, `SudahSelesai`) compute a per-ticket `DurasiHariSaja` with a day filter keyboard; Go intentionally exposes the same five fixed buckets as the received report instead of per-day filtering.

`GET /api/v1/complaints/reports/sent-summary` is the rekapitulasi kirim (`CchRekapKirim*` family). It groups the authenticated origin office's sent complaints by `cchentri.Kantor_Asal` for a required `from`/`to` range, with optional `product_code` (`999` = all) and `regional` selector. `regional` is accepted as either `0`/empty (all regions) or a specific office code; when set it filters offices whose `cch_kantor.Regional` equals the code or that are themselves the regional office, matching the legacy `cch_regional` join. Each row returns office code/name, total sent, completed (`Status_Akhir = '109'`), open (`total - completed`), responded (`total - unresponded`), and unresponded (`Status_Akhir = '101'`), with two-decimal percentages; the legacy MPC-Jakarta cap (`completed > total` is clamped to total) is preserved by deriving open from the clamped completed count. The breakdown is computed in one grouped query rather than the legacy row-per-query loop, uses bounded pagination, returns no contact PII, and is `private, no-store`. It requires `List` on `cchentri` and `cch_kantor` with consistent office/role/report-to. Regional grouping of the detail links and the Excel-HTML export remain unported; CSV/JSON representation here is a deliberate narrow slice.

`GET /api/v1/complaints/call-center/open/export` exports the existing bounded (maximum 100 rows) open-ticket projection to CSV. It requires both `List` and `Export` on `cchentri`, role `3`, consistent revalidated office/role access, and the same origin-or-exact-`Semua_Tujuan` open-ticket filter. Fixed columns omit customer contact data; formula-like cells are prefixed as text and responses are no-store. Broader report exports have separate legacy filters and are not represented by this endpoint.

`GET /api/v1/complaints/call-center/completed`, `GET /api/v1/complaints/call-center/completed/{id}`, and `GET /api/v1/complaints/call-center/completed/{id}/history` are the completed-ticket read slices. They use the legacy `cchselesai`/`cchselesaimas` semantics (`Status_Akhir = '109'`) and the Call Center `recordsetSelecting()` routing fields (`Kantor_Asal`, `Kantor_Tujuan`, exact `Kantor_Tembusan` membership). History is returned chronologically after the parent ticket is proven visible. `GET /api/v1/complaints/call-center/completed/count` is intentionally separate and follows the legacy dashboard count predicate (`Kantor_Asal OR Semua_Tujuan`) with optional complaint-date range. These policies remain read-only; broader completed reports and dashboard counters are not implemented.

The tested Go detail use case requires `View` permission on `cchentri`, the single Call Center role ID `3`, a DB-revalidated office, and a parent ticket whose current status is not `109` and whose routing contains that office as origin or an exact `Semua_Tujuan` token. It returns name/contact/address and complaint narrative because those fields are present on the legacy `CchentriView`; it omits `ID_Pelanggan` and audit columns. The repository query returns the same not-found result for an unknown ticket and a ticket outside the office/status scope. This is deliberately narrower and more explicit than the legacy detail route's filter-dependent hook. Its HTTP route is absent by default and enabled only through the explicit opt-in composition after DB/JWT prerequisites pass.

`GET /api/v1/complaints/call-center/:id/status-options` is a read-only affordance for the status workflow. It independently requires `View cchentri` plus `Add cchentrimas`, role `3`, and matching DB-revalidated office/role across both ACL reads. Its repository requires `cchentri.Kantor_Asal` to match the reviewer office, requires parent status not `109`, and only selects active `cch_jenis_penanganan` IDs `103` and `109`, matching the origin-office branch of the legacy lookup.

## Complaint Entry Lookups

`GET /api/v1/complaints/call-center/lookups` returns active complaint types (`cch_jenis_pengaduan.Status_Aktif = 'Y'`), active intake sources (`cch_sumber_pengaduan.Apakah_Aktif = 'Y'`), the origin office code from DB-revalidated account access, active destination offices (`Sebagai_Tujuan = 'Y'`, excluding the origin office), and active copy offices (`Sebagai_Tembusan = 'Y'`, excluding `40005CC`, `40005PI`, and the origin office). It also returns shipping-service options from `cch_jenis_layanan` and shipment-office options from `cch_kantor`; the legacy CCH add lookup does not apply an active filter to these two lists. It requires `Lookup` permission on `cchentri` and exactly one user level, Call Center (`3`). Request-supplied office values are not used, and the endpoint does not return customer profiles. Ticket status is not returned because status `101` must be server-owned at ticket creation; customer matching is a separate protected workflow.

`GET /api/v1/complaints/call-center/customers/search?q=...` searches customer profiles by name or phone prefix, only within `cchentricus.Kantor_Tambah` matching the DB-revalidated Call Center office. It requires `Lookup` on `cchentricus` and exactly role `3`, rejects prefixes shorter than three characters, escapes SQL `LIKE` wildcards, and caps results at 20. `GET /api/v1/complaints/call-center/customers/{id}` resolves one canonical profile by positive ID under the same trusted office scope; unknown and out-of-office profiles both return `404`, and the response is `private, no-store`. Both endpoints return only snapshot fields and never prove identity or phone ownership. ## Role-Specific Status and Follow-Up Behavior

- `CurrentUserLevel()` returns the active user-level ID; permission masks are separate. The legacy role helpers compare the active ID to one fixed level at a time. Multi-level users and how an active role is selected in a stateless Go API still need an explicit contract.
- `Cchentrimas` has no office restriction in the inspected recordset-selection hook (the candidate filter is commented out). Adding status is separately guarded: non-admin users cannot append after status `109`; Call Center can add history only for tickets whose `Kantor_Asal` is their office.
- Status lookup options depend on the ticket's original office and active role. The origin office gets active statuses `103` and `109`; non-origin UPT, UPT Bandara, Call Center, and Admin UPT get `102`; Kantor Pusat/Admin Pusat get `102` or `109`; other roles compare their office with the origin's regional office to decide whether `109` is available. These are UI/model hooks, not a complete authoritative transition matrix; reconcile status master data and permissions before implementing writes.
- The normal `CchentriList` detail-add link opens `CchentrimasAdd` with `showdetail=cchentrimas`. `USE_TRANSACTION` is configured `true`; the generated add page begins a transaction only when a detail-table context is present. In that normal path, the pre-insert hook creates `cchentridet` rows and the history insert is committed/rolled back together. The post-insert hook runs after commit, then updates `cchentri` status snapshot and `Durasi_Antar_Status`; a failure there can leave committed history/distribution with a stale parent snapshot. Direct/alternate add paths without detail context need explicit acceptance tests.
- The generic `/api/add/{table}` route dispatches through `ApiController` to the table's generated API Add page. For `cchentrimas`, `getCurrentDetailTable()` reads PHP-session state; `addRow()` starts its transaction only when that context is set. The current Go gateway does not establish this legacy PHP master/detail session. Forwarding status Add without a proven session/transaction contract could commit `cchentridet` routing rows separately from `cchentrimas`; `rowInserted()` updates the `cchentri` snapshot afterward. Do not expose status mutation yet. A dedicated legacy API action with an explicit transaction and idempotency/correlation contract, plus failure-injection tests, is the required boundary.
- The inspected `rowInserting()` rechecks terminal status `109` and Call Center origin-office ownership, but role-specific transition choices are primarily added by `lookupSelecting()` (UI lookup). A Go command must validate the requested transition and active master status server-side; never treat allowed dropdown choices as authorization. No dedicated `cchentrimas` API route was found in `src/apiroutes.php`; legacy status routes are web routes through `PermissionMiddleware`.
- `Cchselesai` is a view over status `109`. Its list hook scopes non-admin UPT, UPT Bandara, Admin UPT, Regional, and Admin Regional by origin/destination/tembusan; this differs from the dashboard completed-count predicate and from the general complaint list.
- Follow-up views have their own behavior. `cchfual`/`cchfuhi` deliberately leave a candidate office filter commented out for UPT, UPT Bandara, Call Center, and Admin UPT so a user can see related offices' follow-ups; selected roles get an empty-result filter when no search filter is supplied. Regional follow-up queries add descendant-office scope only for a date-range search. Do not infer these rules from complaint visibility.
- Therefore BE modules should own separate policies for complaint visibility, status-history mutation, completed complaints, and follow-up assignment/visibility. A generic `OfficeScope` shared across these modules would not preserve legacy semantics.

### Status Mutation Boundary Checkpoint (2026-10-01)

The `Cchentrimas` hooks establish the legacy write sequence more precisely:

1. `rowInserting()` rejects a closed parent, assigns the acting office, username, timestamp, and `GetIDHistori()` value, then derives destination offices from the complaint's origin, destination, and copy offices plus each office's `cch_kantor.Regional` value. It inserts the `cchentridet` rows before the history row is inserted.
2. The generated Add page wraps that pre-insert work and the `cchentrimas` insert in a transaction only when PHP session master/detail context is present.
3. `rowInserted()` runs after that transaction. It updates the `cchentri` status snapshot and request status, then computes duration from the latest two history rows ordered by `ID_Histori` and updates the new history row. A failure here can leave history/distribution committed with a stale parent or missing duration.

All three business tables are InnoDB in the inspected schema dump, so one explicit Go SQL transaction could atomically write history, distribution, and the parent snapshot. That alone is not a safe boundary while the legacy Add path remains an independent writer: its hook does not acquire the same parent-row lock, and it has no durable request idempotency key. A Go transaction cannot prevent a concurrently running PHP request from later overwriting the snapshot.

The existing Call Center `status-options` endpoint is not state-specific: for an open ticket originating at the Call Center office, it returns active `103` and `109` independent of the current status. The inspected `rowInserting()` guard rejects status `109` parents and verifies the Call Center origin, but does not impose another current-to-next status rule. The narrow Go compatibility policy therefore accepts any expected open status to active `103` or `109` for role `3` at the origin office; other roles remain out of scope. The legacy history ID is a timestamp with only two subsecond digits and is not a durable replay key.

Under the current constraint that legacy PHP remains untouched, the Go-owned status writer is implemented as a narrow domain/repository/controller slice and registered only behind independent opt-in gates. It is still not production-ready until all of these gates are met:

- Apply `migrations/0001_create_status_transition_idempotency.sql`; startup checks that the table exists and fails closed if it does not.
- Ensure deployment fences the legacy status Add path while the Go writer is enabled. `CCH_LEGACY_STATUS_WRITES_FENCED=true` is an operator assertion, not proof; verify the edge/access-control rule with an acceptance test. Running both writers concurrently is unsupported.
- Keep the API default-off and enable only after coordinated legacy JWT key rotation, least-privilege DB permissions, isolated MariaDB integration/failure tests, and rollout/rollback review.
- Expand tests to cover each SQL failure point, two concurrent commands with different keys and the same expected status, exact replay after uncertain commit, and distribution parity fixtures. Current automated coverage uses sqlmock; no live DB was contacted.

The route is `POST /api/v1/complaints/call-center/{id}/status`, controlled by `CCH_ENABLE_CALL_CENTER_STATUS_WRITE_API` independently of complaint reads. It requires an `Idempotency-Key` header and a strict JSON body with `expected_status_code`, `status_code`, and `description`; initial application returns `201`, exact replay `200`, stale status/key conflict `409`, and inaccessible/ineligible ticket `404`. All responses are no-store. The generic legacy `/api/add/cchentrimas` gateway remains unsuitable because it does not establish PHP session detail context or a durable idempotency contract.

Legacy routes `/cchsettings{list,add,view,edit,delete}` are defined in `src/routes.php` and dispatch through `CchSettingsController` plus `PermissionMiddleware`; there is no API variant in `src/apiroutes.php`. The owner table `cch_settings` has `Option_ID INT UNSIGNED AUTO_INCREMENT` primary key, `Option_Default`/`Show_Announcement`/`Use_Announcement_Table`/`Maintenance_Mode` enum `Y/N` defaulting to `N`, `Maintenance_Finish_DateTime DATETIME NULL`, and `Auto_Normal_After_Maintenance enum('Y','N')` defaulting to `Y`; the live dev schema has 1 row. Unlike pure master data, `LoadApplicationSettings()` in `src/userfn.php` executes `SELECT * FROM cch_settings WHERE Option_Default='Y'` once per session and drives the runtime `MS_MAINTENANCE_MODE`, `MS_MAINTENANCE_END_DATETIME`, announcement flags, then `My_Global_Check()` enforces maintenance mode per page. Legacy row hooks (`rowInserting`/`rowUpdating`/`rowDeleting`) return `true` without side effects. The Go slice (default-off `CCH_ENABLE_APP_SETTINGS_API`) therefore requires the matching action per endpoint and **forbids deletion** (`DELETE` maps to `400`) so the default row is never removed; maintenance on requires a finish datetime; second default maps to `409`. Acceptance tests use mocks only; no live settings row was read or written.

### Help Category Master CRUD

The legacy routes `/cchhelpcategorieslist`, `/cchhelpcategoriesadd`, `/cchhelpcategoriesview`, `/cchhelpcategoriesedit`, and `/cchhelpcategoriesdelete` dispatch through `CchHelpCategoriesController` and `PermissionMiddleware`. `cch_help_categories` stores `Category_ID INT AUTO_INCREMENT`, `Language CHAR(2)`, and `Category_Description VARCHAR(100)`; the model's insert/update/delete hooks return success and add no other side effects. Its language selector reads `cch_languages`. `cch_help.Category` points to the category ID without a database FK, and category descriptions are resolved from the current master row rather than copied into help entries.

The Go slice is isolated under `internal/modules/masters/helpcategories`, gated by default-off `CCH_ENABLE_HELP_CATEGORY_MASTER_API`. Each CRUD endpoint checks the corresponding CCH `List`, `View`, `Add`, `Edit`, or `Delete` action; the language options endpoint checks `Lookup`. Writes verify the supplied language code exists. Deletion locks the category and rejects it with `409` if a help entry currently references it, protecting existing content instead of creating orphaned help rows. This differs from the unguarded legacy hook and cannot prevent a concurrent legacy help insert because the schema has no FK or shared lock protocol; coordinate writers and keep the gate disabled until that operational boundary is addressed. Tests use sqlmock/stubs; no live CCH database was accessed.

### Help Article CRUD

Legacy `/cchhelplist`, `/cchhelpadd`, `/cchhelpview`, `/cchhelpedit`, and `/cchhelpdelete` route through `CchHelpController` and `PermissionMiddleware`; `/cchhelppreview` is a separate preview route. `cch_help` stores an auto-increment `Help_ID`, `Language CHAR(2)`, `Topic VARCHAR(255)`, required `Description LONGTEXT`, integer `Category` and `Order`, `Display_in_Page VARCHAR(100)`, and nullable `Updated_By VARCHAR(20)`/`Last_Updated DATETIME`. Language and category are lookup references to `cch_languages` and `cch_help_categories`; the table has no foreign keys. `recordsetSelecting`, row selection, insert/update/delete hooks add no extra scope or side effects. `Updated_By` and `Last_Updated` are auto-update values in the legacy model.

The Go `internal/modules/help` API is independently gated by default-off `CCH_ENABLE_HELP_ARTICLE_API`. List/View/Add/Edit/Delete and Lookup each require the corresponding CCH action on `cch_help`; no role bypass is added. List supports exact language/category/display-page filters and bounded pagination, returning summaries without `Description`; detail returns the full body. Create/update lock and validate both reference rows and write `Updated_By` from the verified identity and `Last_Updated` using MariaDB time. Delete is physical, matching the legacy delete behavior. The API treats `Description` as opaque content and does not render/sanitize HTML. The legacy preview renderer is not implemented; future clients must safely encode/sanitize content before rendering. Tests use sqlmock/stubs only, with no live CCH database access.

## Backend Completion Gate Before FE

The new backend is ready for FE development only when every required product workflow, not merely every legacy controller name, passes these gates:

- **Domain ownership:** each capability has one Go domain package with service/use case, repository contract, SQL adapter where needed, HTTP controller, DTOs, and explicit dependencies.
- **Legacy traceability:** each workflow records its legacy route/controller/model hooks, owner tables/views, side effects, role/office scope, and intentional differences.
- **Authorization:** every read and mutation validates current account state, table/action permission, active role, office scope, and closed-ticket rules on the server. Client office/role/status values are never trusted.
- **Data consistency:** related writes define transaction boundaries, locking/concurrency, idempotency/retry, and recovery for partial or uncertain results. Direct writes to legacy ticket tables are forbidden unless the ownership boundary is explicitly approved.
- **API contract:** request/response DTOs, validation limits, pagination, error statuses, request IDs, PII/no-store behavior, and feature flags are documented and tested.
- **Acceptance evidence:** positive, negative, authorization, scope, validation, duplicate/replay, closed-record, and failure-injection tests exist; focused tests pass before the full suite.
- **Operational gate:** secrets, JWT rotation, least-privilege DB/API accounts, retention, edge rate limits, observability, backup/recovery, and rollout/rollback procedures are defined before enabling a business flag.
- **FE handoff:** an OpenAPI or equivalent endpoint contract, stable error codes, fixture data, and a compatibility policy are required per workflow. The guest intake submission and CS review contracts are stable enough for a narrow FE slice; this does not imply that other workflow contracts or the overall backend parity gate are complete.

The legacy route inventory contains 95 unique controller families. They will be migrated by workflow families: complaints/status, follow-ups, documents, customers/masters, completed/reporting, administration/support, and AI/external integrations. Generated CRUD aliases do not count as parity unless their business behavior and authorization are covered.

## FE Domain Handoff (2026-10-07)

The first React FE slice is limited to guest intake submission and Call Center draft review, matching `internal/modules/intake/submission` and `internal/modules/intake/review`. FE source mirrors those boundaries: `features/intake/submission` owns its page, step components, and guest API client; `features/intake/review` owns its queue/detail pages, profile picker, ticket-verification components, and staff API client. `app` contains route/layout composition and guards; `shared/api` contains only the common fetch/error transport. Do not move domain behavior into a generic page, service, or components directory.

The FE uses `POST /api/v1/intake/sessions` and `POST /api/v1/intake/submissions` with the browser Origin allowlist and `X-Intake-Session`; review uses the four `intake/review` routes with `X-Authorization: Bearer <staff JWT>`. CCH-BE has no staff login endpoint, so the current FE token form is a session-token adapter only; it does not authenticate users locally or assert name/office. The server remains authoritative for JWT, role, ACL, office, consent, profile matching, identity attestation, and ticket creation.

The guest endpoints have no public reference lookup for complaint type, shipping service, or office codes. Do not invent code labels or copy live CCH rows into the FE. Current intake accepts the CCH codes; a public, allowlisted reference-data contract is required before production customer use. All corresponding BE feature flags remain default-off; implementing a client does not enable a route. Broader complaint dashboard/list, status, follow-up, document, master/admin, reporting, and AI FE domains remain unimplemented.

## Incremental Migration Plan

Migrate by business workflow, not by bulk-generated controller/model count. Each slice should cover one user action end-to-end, stay in its domain package, and stop at its acceptance gate before the next slice begins.

1. **Status lifecycle boundary:** implemented for the narrow Call Center origin path using a Go-owned transaction plus durable idempotency table. Apply the migration, prove the legacy writer fence, and run isolated MariaDB failure/concurrency tests before enabling.
2. **Status mutation vertical slice:** initial Call Center origin transitions to active `103/109` are implemented behind a separate default-off flag. Expand role and transition coverage only after parity review and accepted active-role semantics.
3. **Follow-up write slices:** Call Center plan creation, realization, edit, and cancel are implemented behind independent default-off flags. Wider role scopes and MariaDB concurrency/failure verification remain.
4. **Document lifecycle:** metadata, private-store upload, malware scanning, verified download, inline preview, and office-owned delete are implemented behind separate default-off flags. Retention/deletion policy, deployed scanner/storage checks, backup/recovery, and static-serving fence remain.
5. **Customers and masters:** implement customer CRUD and each master domain independently with its legacy validation and references; avoid one generic CRUD route that bypasses field-specific hooks.
6. **Completed tickets, reports, dashboards:** port each query/predicate separately because legacy office scopes differ; compare query results against isolated fixtures before exposing endpoints.
7. **Administration and support domains:** users/roles/settings, regional/CS-officer management, announcements/help/navigation, with explicit admin authorization and audit requirements.
8. **AI and external integrations:** connect FE through Go to FastAPI; add Track & Trace only after a real provider/data contract, privacy classification, timeouts, and human fallback are approved.

For every slice, record the legacy route/controller/model hook and owner tables, define HTTP contract and acceptance cases, implement domain service/repository/controller, run focused tests before full regression, then update this parity table and history. Keep feature flags off until the slice has passing tests and approved operational prerequisites. Never paste an entire generated legacy module into one implementation batch.
